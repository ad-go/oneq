tunmesh-pq/v2

Wire protocol specification of the oneq mesh network: message formats, key derivation, transcript, threat model and the limits of guarantees.

Status: educational project, without an independent cryptographic audit and without a formal proof. This document describes what the code does (meshproto.py, oneqtunel.py, oneqnode.py, client/core/src/wire.rs) and the security arguments are informal. Do not use this protocol to protect anything you cannot afford to lose. See section 12 for what oneq does not guarantee.

1. Conventions and scope

  • a || b is byte concatenation. All integers in headers are big-endian (u32, u64). Offsets count from 0.
  • The words MUST, MUST NOT, MAY have the meaning from RFC 2119. What is not marked that way describes the behavior of implementations.
  • H(x…) = SHA-256 over the concatenation of arguments. KDF(salt, ikm) is defined in section 5.
  • Roles: I = initiator (sends INIT), R = responder. S_x = static public key of x (1216 B), s_x = corresponding private key.

What this document covers

Covered: the hybrid handshake, the encrypted data plane between two members, fragmentation messages, PUNCH and the M_RLY operations of delegated nodes. Transport (direct UDP, or datagrams carried by oneqrelay over WebSocket with the frame node_id(16) || datagram) is treated only as an insecure channel.

Not covered (described only as an assumption): the oneqrelay registry API, user authentication (password, token), federation between oneqrelay instances, TLS to the registry, STUN/NAT classification. These decide who is a member and what public keys each has; see section 11.

3. Identity and roles

3.1 Static key

Each node has a hybrid static pair:

  • private key (96 B on disk, base64): x25519_secret(32) || mlkem768_seed(64);
  • public key S (1216 B): x25519_public(32) || mlkem768_ek(1184). We write S.x (first 32 B) and S.k (remaining 1184 B).

3.2 node_id

node_id = SHA-256(S)[0:16] (16 B). This is the identifier in the registry, in the INIT header and in relay frames.

3.3 Key ↔ id binding and the source of trust in keys

The public keys of other members come from the oneqrelay registry. A node MUST ignore any registry entry for which SHA-256(S)[0:16] ≠ node_id (checked in oneqnode.apply_members). This prevents the registry from changing the key of an existing node_id, but does not prevent it from introducing a new member (different node_id, different key) or removing a member and assigning its IP/MAC address to another key. There is no key pinning outside the registry; see section 12.1. Registration of a node at a oneqrelay can prove possession of the private key via a KEM challenge (oneqpop.py, outside the data protocol): it prevents an account holder who does not have the key from registering or overwriting the node's entry, but not a compromised registry.

3.4 Initiator / responder role

For each pair of members, the initiator is the one with the lexicographically smaller S over the 1216 B (S_a < S_b ⇒ a is I). Exactly one end initiates. A node that receives INIT from a peer for which it is itself the initiator ignores it.

5. Key derivation

5.1 The KDF function

KDF(salt, ikm) = HKDF-SHA256( salt = salt,
                              IKM  = ikm,
                              info = "tunsec-pq kdf"  (13 ASCII bytes),
                              L    = 64 )
                 = T(1) || T(2)          (RFC 5869: PRK = HMAC(salt, ikm))

All ML-KEM and X25519 secrets are 32 B. The ML-KEM secret comes before the X25519 secret in each IKM (the X25519MLKEM768 order from TLS). Below, inputs appear in exactly the concatenation order.

6. Transcript

The transcript is a chain of hash values h plus a chaining key chain ck. h enters each IKM and is the AAD of each handshake AEAD, so any modified byte in the message or in the static identities changes the keys and causes the tag to fail verification.

6.1 What the transcript binds

  • version and suite (via LABEL in ck0);
  • both complete static public keys (not just node_id), so session keys are bound to the identity pair;
  • INIT header (including idx_i and node_id_i) and RESP header (idx_r, idx_i): an attacker cannot change indices without breaking the tags;
  • all ephemeral keys and all KEM ciphertexts (E_i, ek_e, ct_sr, E_r, ct_e, ct_si);
  • the timestamp (via enc1 in h2).

6.2 What the transcript does NOT bind

  • network addresses (IP/port) or the path (direct / relay / delegated node) over which the messages traveled;
  • FRAG headers (msg_id, index, total): the reassembled message is authenticated, fragments are not;
  • the confirmation from I (the empty DATA packet sent after RESP) is not part of the transcript: R installs the session immediately after a valid INIT, before knowing that I received RESP;
  • h4 (see above).

7. Handshake procedure

   I (initiator)                                              R (responder)
   ─────────────                                              ─────────────
   generates e_i, (dk_e, ek_e)
   (k_sr, ct_sr) = Encaps(S_r.k)
   h0, h1; K1 → ck1, k1
   enc1 = AEAD(k1, ts, aad=h1)
                         ── INIT ──────────────────────────▶
                                                              checks length/type, node_id → known peer,
                                                              role, budget; k_sr = Decaps; K1; verifies enc1
                                                              verifies ts (replay/skew)
                                                              generates e_r; Encaps(ek_e), Encaps(S_i.k)
                                                              h3; K2 → ck2, k2; enc2; K3 → transport keys
                                                              INSTALLS session
                         ◀────────────────────────────── RESP ──
   verifies lengths, idx_i == mine
   k_e, k_si = Decaps; K2; verifies enc2
   K3 → transport keys; INSTALLS session
                         ── DATA (empty payload) ─────────▶  (R learns I's address)

7.1 Initiator

  1. Chooses idx_i (random, ≠ 0, unused), generates e_i and (dk_e, ek_e).
  2. Computes (k_sr, ct_sr), h0, h1, dh1, dh2, K1; enc1 with ts = current clock in µs.
  3. Sends INIT (fragmented) on all candidate paths (UDP to peer's endpoints; via oneqrelay if no endpoint or after relay_after = 10 s without session). Retries every HS_RETRY = 2 s while no session; keeps at most 4 pending states, each for 10 s.
  4. On RESP: rejects if length or type is wrong or if the echoed idx_i doesn't match a pending state; then k_e, k_si, K2, verifies enc2; on any AEAD error silently drops the message. On success computes K3, installs the session (send = k_i2r, recv = k_r2i) and immediately sends a DATA with empty payload.
  5. Renewal: if the current session is ≥ REKEY_AFTER (120 s), I repeats the handshake. The old session remains as previous (receives) until it expires or is replaced.

7.2 Responder

Check order (cheap → expensive), each failure = silent drop:

  1. length exactly 2349 B and type 0x21;
  2. node_id_i belongs to a known member in the registry, and the local role is R (otherwise the node can refresh the registry);
  3. if INIT came via oneqrelay, src_id from the frame equals node_id_i;
  4. token bucket (init_budget) has ≥ 1 token;
  5. node_id_i == SHA-256(S_i)[0:16] for the key in the registry;
  6. k_sr = Decaps, dh1, dh2, K1, tag verification of enc1 with AAD h1;
  7. ts > last_ts[peer] (strictly) and |now − ts| ≤ max_skew (180 s); then last_ts[peer] = ts. last_ts is in memory, lost on restart;
  8. chooses idx_r, generates e_r, builds RESP, computes K3, installs the session (send = k_r2i, recv = k_i2r) and sends RESP on the path INIT came from.

A responder's session becomes current immediately; the previous one remains as previous. A DATA packet is tried on the session whose local_idx equals receiver_idx.

8. Data plane

8.1 Sending

  1. If age ≥ REJECT_AFTER or counter ≥ MAX_COUNTER the session no longer sends.
  2. hdr = type || remote_idx || counter; counter increases by 1; ct = ChaCha20-Poly1305(k_send, 0⁴ || counter, payload, aad = hdr); the datagram is hdr || ct.

8.2 Receiving

  1. Length ≥ 29 B, type 0x23 or 0x24, age < REJECT_AFTER.
  2. receiver_idx → session (current or previous) with that local_idx; otherwise drop.
  3. Replay check before decryption: counter must be larger than the largest seen, or within the last 1024 counters and not yet seen.
  4. Decryption with k_recv; on failure drop. Only on success is the counter marked as seen.
  5. The peer's path (source address) is updated after authentication.

8.3 Frame delivery (L2)

After decryption, a payload ≥ 14 B is an Ethernet frame. The node drops it if: length is < 14 or > MTU + 22; the source address has the group bit set or is its own address; the source address is the registered MAC of another member. Otherwise it writes the frame to the TAP interface. No forwarding between peers (no transit).

9. Delegated nodes: RLY (0x24)

A member can send a datagram destined for another member through a delegated node (a member authorized by an administrator in the registry) with which both have a direct session. The RLY packet has the DATA format (§4.3), with type 0x24, the same keys and counter as the session between the member and the delegated node. The decrypted payload is op(1) || body:

opNameBodyDirection
1RLY_FWDdst_id(16) || datagram (datagram ≤ 1600 B)member → delegated node: send the datagram to member dst_id
2RLY_DLVsrc_id(16) || datagram (body length > 17)delegated node → member: datagram from src_id
3RLY_NACKdst_id(16) || reason(1) (17 B)delegated node → member: delivery impossible; reason 1 = destination unreachable, 2 = rate limit

The datagram is a complete packet for the other member (DATA, or handshake fragment): it is protected by the session between the two members, so the delegated node cannot read or modify it undetected. Rules:

  • src_id in RLY_DLV is set by the delegated node; the receiver accepts RLY_DLV/RLY_NACK only from nodes the registry lists as delegated. A fake label produces at most a packet rejected by the session between the members.
  • A node without delegation in the registry ignores RLY_FWD. The delegated node applies a total token bucket (registry quota, kbit/s) and one per sender (half); RLY_NACK at most once per second and per pair.
  • A single hop: a datagram received via RLY is not forwarded further by the node that delivers it.

10. Fragmentation and PUNCH

10.1 Fragmentation

Only INIT and RESP are fragmented. A message is split into 1193 B chunks (the last may be shorter); at most 4 fragments. The receiver reassembles by the key (source, msg_id). A fragment is rejected if: datagram length > 1200 or < 7, type ≠ 0x15, total ∉ [1,4], index ≥ total, a fragment other than the last doesn't have exactly 1193 B, total differs from other fragments of the same message, or the fragment is a duplicate. Limits: lifetime 5 s, at most 16 messages in progress, 4 per source, 64 KiB total. The reassembled message is then treated as INIT or RESP and authenticated via AEAD.

10.2 PUNCH

A node without a session with a peer periodically sends PUNCH toward the peer's endpoints: opens the NAT mapping and tells the peer (if it has a session older than 3 s and is the initiator) that a new handshake may be needed. The receiver reacts at most once every 5 s per peer. Being unauthenticated, PUNCH can be forged by anyone who knows a member's node_id (see 12.3).

11. Threat model

11.1 Assets protected

  • A1. Confidentiality and integrity of Ethernet frames between two members.
  • A2. Endpoint authenticity: a frame is attributed to the member whose static key participated in the handshake.
  • A3. Session keys of past sessions, after subsequent compromise of static keys.

11.3 Trust assumptions

  • Primitives (X25519, ML-KEM-768, ChaCha20-Poly1305, SHA-256, HKDF) are secure and correctly implemented by the libraries used (cryptographic libraries of each implementation: cryptography/OpenSSL in Python, libraries in client/core in Rust).
  • The registry is trusted for membership (who is a member, what key they have), not for confidentiality. The channel to the registry is TLS 1.3 with X25519MLKEM768 key exchange and classical certificates.
  • The system's random number generator is good; private keys do not leave the node.
  • Member clocks are synchronized to ±180 s.

12. What oneq does NOT guarantee

The list below is intentionally explicit. Each point is a real limitation of this version, not a rhetorical assumption.

12.1 Member authenticity depends on the registry

  • A compromised registry (R1) can add a member with their key and can replace a member: delete a node's registration and assign its IP/MAC address to a new key. Nodes accept any consistent entry (node_id = SHA-256(S)[0:16]) that the registry lists. The key ↔ id binding doesn't protect against this: it only protects against changing the key under the same node_id.
  • There is no key pinning (TOFU), out-of-band verification (fingerprints compared by users), or a transparency log. A registry MITM on a new or replaced member is not detectable by others.
  • There is no admin approval for members: any valid account with quota can register nodes (known limitation from ARCHITECTURE.md).

12.2 Metadata and anonymity

  • The protocol does not hide identity: node_id_i is in the clear in INIT, receiver_idx and counter are in the clear in each packet, PUNCH contains node_id in the clear.
  • Packet sizes, timing, volume and counter remain visible; there is no padding, cover traffic or mixing. Traffic types can be inferred from size and timing.
  • The registry and other members learn each node's public IP address (endpoints are published). The oneqrelay sees the (source, destination) pair and the volume of traffic passing through it. A delegated node sees the encrypted packets and the pairs it serves.
  • Does not provide anonymity in the Tor/mixnet sense and does not claim deniability.

12.3 Availability

  • Does not guarantee availability. An on-path attacker can delete, delay or redirect packets; a oneqrelay or a delegated node can refuse service.
  • Asymmetric INIT cost: before tag verification, the responder performs one ML-KEM decapsulation and two X25519 operations. The only defense is the token bucket (10 + 5/s). This is per node, not per peer: anyone who knows a member's node_id (visible in the clear in any INIT) can send fake INITs that consume tokens and delay legitimate handshakes.
  • PUNCH and address redirection: unauthenticated PUNCH can force a re-handshake by the initiator (at most once every 5 s per peer, only for sessions > 3 s). The peer's address is updated on the first authenticated packet received from a different source (as in WireGuard) and on installing a new session; an attacker who retransmits a valid, not yet marked packet from a different address can temporarily redirect traffic, without being able to read or modify it.

12.4 Replay and clocks

  • last_ts (anti-replay for INIT) is only in memory. After the responder restarts, an INIT captured in the last 180 s can be replayed: the responder installs a session (and sends RESP) that the legitimate initiator no longer knows; traffic sent by the responder may be dropped by the initiator until the next handshake (at most ~120 s, or faster via PUNCH). The attacker gets no keys.
  • The protocol relies on the local clock at handshake: a skew > 180 s between two nodes causes the handshake to fail. There is no secure time.

12.5 Quantum security: what it covers and what it doesn't

  • The hybrid protects confidentiality of recorded sessions (Q1) if ML-KEM-768 holds. There is no formal proof of the combiner (concatenation + HKDF with transcript); the argument in 11.4 is informal.
  • A quantum-capable active adversary (Q2) that breaks X25519 in real time can forge an INIT (see 11.4); it gets no transport keys, but can produce unwanted state at the responder.
  • TLS to the registry has the hybrid key exchange, but certificates are classical: registry authentication is not post-quantum. Passwords, tokens (HMAC, 1 h) and the federation secret are not part of this protocol.
  • Does not claim formal resistance to KCI (key-compromise impersonation) and there is no analysis of "unknown key share" attacks.

12.6 Node and key compromise

  • The static private key is stored in a file, unencrypted (the Python implementation refuses to load it if the group or others have access on Unix). Anyone who reads it can impersonate the node until it is revoked in the registry. Revocation is done only through the registry and propagates after replication (seconds).
  • There is no post-compromise recovery other than a new handshake with the same static key: if the attacker has the static key, they can establish new sessions as that node. Forward secrecy (11.4) protects only sessions completed before the compromise.
  • Implementations do not guarantee deletion from memory of ephemeral secrets (Python: no; Rust: as much as the crates used allow) nor constant-time execution beyond what the libraries provide.

12.7 What happens after decryption

  • The protocol authenticates the peer, not the L2 content. A malicious member (M1) can send any Ethernet frame (ARP/DHCP/IPv6 ND, broadcast floods) with their own MAC address. The only rule enforced is that a member cannot use the registered MAC of another member. There are no access lists, inter-member isolation or protocol filtering within the community.
  • A delegated node (D1) cannot read or modify datagrams, but can delete, delay or duplicate them (duplicates are rejected by the destination's anti-replay window). NACK labels can be used by it to make members avoid a path.

12.8 Protocol and evolution

  • No negotiation of version or algorithms: a format change means a new LABEL and new types; v1 and v2 nodes do not interoperate. There is no mechanism for gradually migrating a network between versions.
  • The zero handshake nonce is safe only because k1 and k2 are used exactly once; any protocol modification that would reuse these keys would break security.
  • Full mesh: n² sessions; designed for tens of nodes.

12.9 Process guarantees

  • There is no independent audit, no formal proof (e.g. ProVerif/Tamarin) and no systematic fuzzing. See section 13 for what has been verified.

13. Verification and conformance

What has actually been verified for this document:

  • spec_check.py (at the repository root) contains an independent implementation written only from the formulas in sections 4–6 and 8 (no imports from oneq code). Run on a Mac Intel (Python 3.13.16, OpenSSL 3.5.9, cryptography 48.x), against meshproto.py in both roles, it confirmed: INIT (2349 B) and RESP (2233 B) lengths; equality of ck1 and h2 at the responder; equality of transport keys in both directions; a DATA packet and an RLY packet built per §4.3 accepted by the implementation and vice versa; rejection of an INIT and a RESP with one bit modified.
  • The Rust client (client/core/src/wire.rs) uses the same LABEL, HKDF info, types, lengths and constants (verified by inspection and by its unit tests, which assert lengths 2349/2233 and the types); spec_check.py has not been run against it, and Python ↔ Rust compatibility is exercised by the lab tests and by real project nodes.

What has not been verified: known-answer test vectors (the handshake uses random ephemeral keys and has no deterministic mode), formal analysis, fuzzing, resistance to side-channel attacks, behavior at memory limits.

To redo the verification: python3 spec_check.py with meshproto.py, oneqtunel.py, pqtls.py alongside (Linux or macOS; cryptography ≥ 46).
